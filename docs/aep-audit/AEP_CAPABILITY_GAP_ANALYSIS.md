# AEP Capability Gap Analysis

This assessment is limited to the LiftIQ and adjacent AssetIQ Notifications source available in this checkout. TankIQ, CloudIQ, ReeferIQ and separate backend/service repositories were not available for inspection. “Gap” therefore means evidence not found in inspected code, not proof that the company has no such service elsewhere.

| Capability | Current evidence | Gap / limitation | Recommendation | Confidence and verification questions |
|---|---|---|---|---|
| 1. Shared design system and application shell | Both apps use React/TS and have headings, badges, panels, drawers, buttons and custom CSS. | No shared package, tokens, shell contract or accessibility baseline; app shells and routing differ. | **Standardize** design tokens and product-neutral primitives first; keep shell/navigation composable by product. | **High** in this checkout. Is there an organization design system or Figma spec outside these repos? |
| 2. Reusable component library | Each app has local UI helpers; LiftIQ has table/chart patterns and Notifications has modal/drawer/toggle helpers. | No published package, registry, component documentation, versioning or test matrix. | **Standardize** only stable low-level primitives; package after two-app validation. | **High**. Which teams own shared UI and product accessibility acceptance? |
| 3. Adaptive dashboard and widget configuration | LiftIQ has hand-authored Dashboard and Personalized Home; notification rules/preferences configure behavior. | No dashboard schema or widget configuration/runtime rendering. | **New capability candidate** after shared component and data contracts. | **High** in inspected source. Which layouts need end-user customization versus product-admin configuration? |
| 4. Application/page configuration schema | Routes/pages are coded in React in both apps. | No page tree, layout schema, validation/versioning, or draft config. | **New capability candidate**, dependent on component contracts, permissions, and schema governance. | **High** in checkout. Which page primitives are safe for customer configuration? |
| 5. Configuration-driven runtime renderer | No inspected app resolves a saved page definition into component instances. | Current components are ordinary React components; no runtime builder/renderer. | **New capability candidate**, begin with limited dashboard widgets rather than arbitrary pages. | **High**. Is a renderer present in a separate builder/runtime repo? |
| 6. Data binding and device schema mapping | LiftIQ uses typed station/message fixtures. Notification integration maps selected alarm lifecycles to a typed event shape. | No device schema registry, metric units/normalization service, query binding, or backend data adapter. Event contracts duplicate and tenant scope is synthetic. | **Standardize** event/asset/metric contracts and adapters before visual bindings. | **High** in checkout. Which device protocols and canonical metric definitions are authoritative? |
| 7. Device and asset abstraction | LiftIQ has `StationRecord`, station/pump types, and asset lists. Notifications has `assetId`/`stationId` on event model. | Product-specific identities and relationships; no shared asset registry or tenant-scoped asset service. | **Refactor candidate**: define identifiers and hierarchy at integration boundaries; retain product-specific asset attributes. | **High**. What is the system of record for customer, site, station, device, and equipment IDs? |
| 8. Shared identity and tenant-aware authorization | Notifications has a simulated role/org selector and client filter; LiftIQ toggles a demo user and uses a static personalization namespace. | No auth provider, server authorization, permission model, token/session flow, or tenant identity on LiftIQ alarm domain. | **New foundational capability** (or integrate an existing identity platform if found); server must derive tenant and enforce every query/action. | **High** in code; **Unknown** outside repo. What identity provider, tenant hierarchy, roles, and policy service already exist? |
| 9. Shared notification service and UI | LiftIQ has a local inbox/bell and proposed event mapper; Notifications has broad local inbox/rule/recipient/delivery/audit UI and adapter fixture. | No live event transport, server persistence, provider delivery, retry, policy engine, authenticated recipient resolution, or source reconciliation. | **Refactor/standardize** the event contract; build/integrate server service with identity, idempotency, delivery policy, and audit. | **High** in apps. Is a production notification service/provider integration already operated elsewhere? |
| 10. Search, history, and export framework | Each app has client-side, page-specific searches/filters; LiftIQ exports local CSV; Notifications has inbox filters and delivery/audit history. | No shared query API/index, cross-product history, consistent filter schema, server paging, export job, or access-scoped search. | **Standardize** filter/query contract, then implement backend search over authorized records; keep product-specific columns/semantics configurable. | **High** in code. Which data stores and retention windows support cross-app search? |
| 11. Rules and workflow configuration | LiftIQ contains alarm lifecycle business rules in TypeScript; Notifications has editable mock notification rules. | No server rule engine, validation/versioning, execution audit, or separation between rule UI and policy runtime. | **Refactor candidate**: separate policy model, evaluation service, and product-specific domain rules. | **High**. Do customer workflows require no-code authoring or only admin-managed policies? |
| 12. Visual no-code application builder | No builder UI or application authoring workflows found. | No canvas/editor, preview, config validation, collaboration, permission or publish controls. | **New capability candidate** after schema/runtime and governance are proven. | **High** in inspected source. Who is the intended author: internal developer, product admin, partner, or customer? |
| 13. Component registry and version management | Local React components and TypeScript event mappings only. | No registry, metadata/manifest, compatibility metadata, release policy, or dependency approval. | **New capability candidate** after reusable contracts and test/isolation requirements. | **High**. Should components be trusted first-party packages, partner extensions, or both? |
| 14. AI-assisted component extension | LiftIQ includes an AskLiftIQ quick helper; source shows local navigation/lookups rather than an AI generation service. | No model/API integration, code generation, isolated build, extension validation, approval workflow, or rollback. | **New capability candidate**, defer until registry, sandbox, automated validation and review gates exist. | **High** for source inspected. Is there a separate AI service or governance policy? |
| 15. Application draft, publishing, and rollback | Vite build outputs exist; app preferences are locally persisted. | No config draft/publish lifecycle, release promotion, environment versioning, or rollback control plane. | **New capability candidate**, dependent on config schema, immutable versions, and access/audit. | **High** in checkout. How are current apps released and rolled back operationally? |
| 16. Deployment control plane | Both manifests expose `build` and `preview`; Vite uses local fixed ports. | No deployment workflow, environment management, customer deployment orchestration, release approval, or rollback definition found. | **Investigate** existing CI/CD first; then standardize pipeline and release metadata before building a control plane. | **Medium**: no deployment files found here, but separate DevOps repos may exist. What platform currently deploys these apps? |
| 17. Terraform/cloud environment provisioning | No `.tf`, Docker, cloud template, or provider config found in inspected paths. | No evidence for infrastructure provisioning, environment isolation, secrets, or automated teardown. | **Investigate** organization cloud foundations; reuse approved Terraform modules if available. Do not start a new provisioner until that inventory exists. | **Medium**. Are AWS accounts/modules managed in a central infrastructure repository? |
| 18. Monitoring, auditing, and lifecycle management | Notifications app has an in-memory audit view; LiftIQ has alarm/activity history; app footers call out prototype scope. | No durable centralized audit, service health metrics, traces, alerting, lifecycle/retention, or environment monitoring config found. | **New/integrate capability**: central telemetry/audit standards for runtime and admin actions. | **Medium**. Which observability and audit platforms are already standard? |

## Cross-cutting decisions before implementation

1. Find the system of record for customer/tenant, user identity, asset hierarchy, device registry, telemetry and alarm lifecycle.
2. Obtain TankIQ, CloudIQ and ReeferIQ repositories and identify their existing frameworks and release boundaries.
3. Obtain production notification, authentication, monitoring and infrastructure repositories or service contracts before declaring those capabilities absent.
4. Establish canonical event/metric schemas, version ownership, unit/timezone semantics, and product extension policy.
5. Decide which customers can configure dashboards/pages and which configurations remain product-admin or developer owned.
6. Define the security model for customer-authored configuration and any future executable extension; generated code needs isolation and explicit review.
